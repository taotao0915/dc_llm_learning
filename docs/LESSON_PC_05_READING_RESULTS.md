## 1. 这节只建立一个检查顺序

结束情况 → 内容质量 → 性能体验。

先问“有没有异常中断或截断”，再问“答案是否满足要求、事实是否可靠”，最后看“响应与生成够不够快”。
一个很快但错误的回答，不能算应用成功；一个正常停止的回答，也不一定完整完成了用户任务。

## 2. 三种状态，不要混在一起

### 程序收到响应

HTTP 请求有返回，说明调用链至少工作到了响应阶段。
连接错误、模型不存在、网络断流，与“模型回答内容错误”不是同一类问题。
若本次请求失败，不能为了填表把缺失的速度或首片时间写成 0。

### 生成正常结束且有正式正文

现有聊天脚本把下面条件记为 `complete=True`：

```python
complete = final.get("done_reason") == "stop" and bool(answer.strip())
```

这只是程序为历史管理使用的条件，不是“内容质量满分”。
`stop` 说明生成正常停止；`length` 提示到达长度限制，应检查回答有没有被截断。
即使正常停止，也可能漏掉用户要求的一部分，仍要读正文。

### 内容符合任务且事实可靠

至少人工检查：

1. 有没有回答用户真正问的问题？
2. 有没有遵守“三句话”“只回答名字”等要求？
3. 有没有错误事实、无依据的绝对化说法，或遗漏关键条件？

在第四课中，上限 8 的答案明显只写了半句话，上限 128 的答案有三句话，但第三句把端侧限制说得过于笼统。
“端侧设备常受算力、内存和功耗约束”比“端侧模型性能较弱，不能支持复杂任务”更准确。
本课查看脚本不会自动给正文打正确率分数，而是明确显示“待人工检查”。

## 3. 性能不只有一个“秒数”

### 指标 A：首个正式答案片段出现时间

字段：`first_answer_chunk_seconds`。
它回答：“发起调用后，我等多久才开始收到正式回答？”
这个等待可能受模型加载、排队、输入处理、思考生成和数据传输等影响。

现有脚本从即将连接服务前开始计时，收到第一个非空 `message.content` 片段时记录。
它是客户端观察指标，不是直接测得的推理引擎内部首 token 时间；若片段只有空白字符，也可能被当前实现计入。

还有 `first_generated_chunk_seconds`：首次收到思考或正式回答片段的时间。
思考模型可能很早开始生成思考，但正式回答较晚出现，因此两者不能混用。
第四课关闭思考，相关两项值在这些记录中相同。

### 指标 B：生成阶段速度

字段：`decode_tokens_per_second`，单位 token/s。
它回答：“模型进入生成阶段后，平均每秒生成多少 token？”

现有脚本用服务端返回的数量和生成耗时计算：

```python
rate = generated * 1e9 / duration
```

其中 `generated` 来自 `eval_count`，`duration` 来自 `eval_duration`，单位是纳秒，所以换算需要乘以 10 亿。
这个数不是汉字/秒，也不是“生成 token 数除以用户等待的全部时间”。
开启思考时，生成数量可能包含思考 token，不能把它直接当成正式答案文字的生成速度。
参考：[Ollama Chat API 的 eval_count 与 eval_duration](https://docs.ollama.com/api/chat)。

### 指标 C：客户端总耗时

字段：`client_total_seconds`。
它回答：“从脚本开始调用，到接收并处理完这轮流式响应，总共多久？”
它包含调用过程中的等待和流式处理，但不包括你输入问题的时间，也不包括之后保存 JSON 报告的时间。
它不是服务端 `total_duration` 字段的同义词，更不是纯生成时间。

## 4. 用旧实验对比这三个指标

| 项目 | 输出上限 8 | 输出上限 128 |
|---|---:|---:|
| 实际生成数 | 8 token | 74 token |
| 首个正式答案片段 | 9.022 秒 | 0.319 秒 |
| 服务端生成阶段速度 | 6.29 token/s | 5.87 token/s |
| 客户端总耗时 | 10.273 秒 | 12.901 秒 |
| 结束原因 | length | stop |

可以得到的观察：

- 第一组等待很久才收到正式片段，最后只有半句话。
- 第二组很快开始显示内容，但因为本次生成的内容多，总耗时比第一组长。
- 第二组生成阶段速度并没有因为首片更早而更高；两项指标描述不同事情。

不能得到的结论：

- 不能说“输出上限越大，首片一定越快”。顺序运行中的加载、缓存、系统负载等没有被控制为完全相同。
- 不能说“第一组 9 秒一定全花在模型加载上”。旧报告没有保存独立加载耗时，不能分解出确切原因。
- 不能把 6.29 与 5.87 的差异当作严格性能排名，两组输出长度也不同。

### 一个简单计算，解释为什么不是同一种速度

第一组按客户端全部用时摊算：8 ÷ 10.273 ≈ 0.78 token/s。
但报告的生成阶段速度是 6.29 token/s。
两者没有矛盾：前者把等待也算进去，后者使用服务端记录的生成阶段耗时，分母不同。
本课保留两种统计口径的区别，不拿总耗时重新覆盖旧报告里的生成速度。

## 6. 看懂两行最基本的读取代码

```python
with path.open("r", encoding="utf-8-sig") as file:
    report = json.load(file)
```

`"r"` 表示只读打开；`json.load(file)` 把整份 JSON 文件还原成 Python 对象。
这里与第三课流式接口逐行使用 `json.loads(line)` 不同：这次读取的是已经保存好的一个完整 JSON 文档。

然后在每次生成记录里找到：

```python
result["done_reason"]
result["answer"]
result["first_answer_chunk_seconds"]
result["decode_tokens_per_second"]
result["client_total_seconds"]
```

完整脚本还处理字段缺失；没有记录的数字显示“未记录”，不冒充测得了 0 秒。

## 7. 写一条自己的实验结论

不用先做复杂统计，可以按照下面四项写：

```text
任务：请模型用三句话解释端侧大模型。
结束情况：stop，正常结束且有正文。
内容检查：三句话形式符合，但对端侧能力的限制说得过于笼统。
性能观察：首片约 0.32 秒，总计约 12.90 秒；属于这次历史样本，不据此保证下一次速度。
```

以后比较模型或参数时，应保持问题和评判标准一致，并记录模型、量化、线程、上下文、输出上限、思考模式等条件。
先重复少量可检查的任务，再考虑更系统的统计；不要从不同任务的一次耗时就宣布某模型更强。
首次加载与已经加载的请求最好分开记录。正式性能测试还需要控制其他负载、输出长度并重复测量，本课尚未做这些。
