# 电脑端第 4 课：上下文、输出预算与温度

日期：2026-10-03。助手已执行本页实验，用户亲自练习和理解情况尚待反馈。
本课只关注三个设置，使用已安装的 Qwen3，不修改现有连续聊天脚本。

## 1. 先建立三个不同的概念

| 设置 | 通俗理解 | 当前连续聊天脚本的值 |
|---|---|---|
| `num_ctx` | 工作台有多大：当前计算可利用的上下文容量 | 4096 |
| `num_predict` | 这次最多允许新写多少 token | 1024 |
| `temperature` | 选下一个 token 时有多保守或多随机 | 0.6 |

这里的“生成参数”是运行设置，不是模型名中 1.7B 所说的“模型权重参数”。
调整这三个设置不会重新训练模型，不会把 GGUF 文件改成一个更大或更聪明的模型。
参考：[Ollama 参数定义](https://docs.ollama.com/modelfile#valid-parameters-and-values)。

## 2. num_ctx：上下文容量，不是永久记忆

可以把上下文想成计算时能摊开的工作台：上面放当前问题、被携带的历史、聊天模板等内容，以及逐渐生成的新内容。
按本课的预算方式，输入和历史需要给输出预留空间；不能理解成“输入先用满 4096，再额外白送 1024 输出”。
超过预算时怎么办，取决于应用和推理实现；我们的聊天脚本会提前裁剪最早的完整问答对。

例如现有聊天脚本里：

```python
budget = OPTIONS["num_ctx"] - OPTIONS["num_predict"] - 128
```

在 4096 上下文、1024 输出上限时，这个应用层预算等于 2944。
这里额外预留的 128 是教学脚本选定的安全余量，不是 Ollama 要求的固定值。
更重要的是：脚本用 UTF-8 字节数加消息开销做保守估算，2944 **不是精确可输入的 token 数，更不是汉字数**。
后续才学习模型 tokenizer 的精确计数。

上下文更大通常需要更多推理内存，但不保证答得更准，也不会自动恢复未发送或已裁剪的历史。
先保留本机已验证的设置，不要为了“让模型更聪明”盲目把上下文拉满。
参考：[Ollama 上下文长度说明](https://docs.ollama.com/context-length)。

## 3. num_predict：输出上限，不是必须达到的长度

假如设置：

```python
"num_predict": 128
```

意思是最多生成 128 token，不是必须生成 128 token，也不是最多 128 个汉字。
模型可能提前正常结束；也可能还没说完就用光额度。
如果开启思考生成，思考内容也会消耗生成额度；这次实验固定 `think=False`，没有观察到非空思考输出。

以前 DeepSeek 先思考、耗尽预算却没正式答案，就是输出预算与生成行为共同作用的例子。
但后来名字答错且正常 `stop` 的问题不能因此一概用“再增加输出预算”解决。

### 本机真实对照：只改输出预算

两次都使用同一个问题、Qwen3、4096 上下文、temperature=0.6、seed=42、CPU 4 线程、`think=False`。
问题是：

```text
请用三句话解释什么是端侧大模型：第一句说明运行在哪里；第二句说明一个优点；第三句说明一个限制。
```

| 输出上限 | 实际生成 token | 结束原因 | 正式回答情况 | 本轮总耗时 |
|---|---:|---|---|---:|
| 8 | 8 | `length` | 只说到“端侧大模型是指在终端设备” | 10.273 秒 |
| 128 | 74 | `stop` | 生成了三句话 | 12.901 秒 |

两次服务报告的输入 token 数均为 45。
128 这一组只用了 74 token 就结束，是“上限不是目标长度”的直接例子。
8 这一组输出被截断是特意设计的观察对象，不是程序运行失败，不必删除这份结果。
第二课复用函数会提示“缩短问题后重试”；第四课实验另加提示说明本组故意限制输出，应先比较下一组。

128 组原始回答全文：

> 端侧大模型是指在终端设备（如手机、平板、物联网设备等）上运行的大型模型，不依赖云端服务器。
> 它的一个优点是能够实现本地化处理，减少数据传输和隐私泄露的风险。
> 然而，端侧大模型通常资源有限，性能较弱，难以支持复杂的任务和高精度的推理。

质量检查：它完成了三句话，但第三句说得过于笼统。更准确地说是端侧设备常有算力、内存、功耗限制，
需要在模型大小、速度和效果之间取舍，不能仅凭“端侧”断言一定性能弱、不能完成复杂任务。
本课再次区分：程序能运行、回答完整、回答正确，是不同检查项。

这些耗时含加载、输入处理、生成等因素；未统一冷启动和缓存状态，不能据此计算提高上限会让推理速度降低多少。

## 4. temperature：影响随机性，不控制温度或智力

模型生成文字时，会为接下来可能出现的 token 给出不同倾向。
较低温度通常更偏向高概率选项；较高温度让其他候选有更多被选中的机会。
这不是“低温一定正确、高温一定错误”，也不是“高温会获得更多知识”。
它不指 CPU 温度，不直接增加上下文容量或输出上限。

### 本机真实对照：为咖啡馆取名

统一问题：

```text
为一家适合学习编程的咖啡馆取一个中文名字，只输出一个名字，不超过六个汉字。
```

保持模型、问题、上下文 4096、输出上限 128、CPU 4 线程和关闭思考不变。
选 seed=42、43、44 作为三个配对条件，每一对内只改变 temperature：

| 同一对使用的 seed | temperature=0.2 的实际回答 | temperature=1.0 的实际回答 |
|---|---|---|
| 42 | 码咖屋 | 码咖馆 |
| 43 | 码咖屋 | 码咖屋 |
| 44 | 码咖屋 | 码咖馆 |

6 次都正常 `stop`，都报告生成了 4 token。
提高温度后有两对名字变化，也有一对没变，说明它改变选词倾向，不保证每次输出不同。
这只有 3 对样例，不是可靠的多样性统计，更没有证明哪个名字质量更高。
0.2 与 1.0 是为了演示对照选择的值，不是对 Qwen3 的最优参数推荐。

`seed` 是随机数种子，能帮助对照；不能当作跨所有运行状态都绝对复现的保证。
跨对改变 seed 是为了观察不同条件，同一对内部仍然只改变温度。

## 5. num_ctx 的小实验：只看应用怎样裁剪历史

这一部分没有请求模型。它构造 4 轮示例问答，调用第二课真实的 `prepare_messages` 函数。
输出预留统一设为 128，额外安全余量仍是 128，只改变 num_ctx：

| num_ctx | 应用预算数值 | 裁剪掉的最早问答轮数 | 最终消息条数 |
|---|---:|---:|---:|
| 2048 | 1792 | 2 | 5 |
| 4096 | 3840 | 0 | 9 |

4 轮历史本来包含 8 条消息，加当前问题就是 9 条。
裁剪 2 轮意味着拿掉 4 条历史消息，剩下 5 条，而不是随意拿掉单个 user 或 assistant 消息。

这证明当前应用的预算和裁剪逻辑发生变化，不是在测 Qwen3 的记忆准确率，也没有测实际内存占用。
数值比较使用字节估算，不要把这里的预算或文本长度标注成真实 tokenizer token 数。

## 6. 在 PyCharm 直接运行

打开：`scripts/generation-parameters-lab.py`，右键 Run。
代码只用 Python 标准库，复用旁边的 `chat-with-history.py`，不需额外安装包。

菜单是：

```text
1 输出预算：2 次请求 | 2 上下文裁剪：无需模型 | 3 温度：6 次请求
选择 1/2/3，直接回车先做 1：
```

先输入 `1`，或直接回车。这一轮先只观察三个值：

1. `num_predict` 设置的上限。
2. 报告里的 `generated_tokens_including_thinking`：服务报告的实际生成数。
3. `done_reason` 是 `length` 还是 `stop`。

控制台会显示答案、耗时、输出上限、实际生成数、结束原因和报告路径。这些结果也可在报告 JSON 的每个 `entries` 条目下的 `result` 中找到。
每个生成实验只发送当前问题，不把前一组输出带进下一组，避免历史不同造成额外变量。
实验选项只在本脚本的 Python 进程中暂时覆盖，结束会恢复，磁盘上的连续聊天脚本和模型文件不变。
本课实验默认生成上限 128；第二课自由聊天原来的 1024 仍保留，不要把两份设置混淆。

完成 1 后再重新运行、选择 2；有余力再选择 3。不要求一次学完或运行全部组。
1 和 3 需要本机 Ollama 启动且已有模型；2 不连接服务也能运行。
出现连接错误时保留报告并检查服务，不要把网络错误解释为模型质量差。

报告保存到学习目录 `output/generation-parameters/`，每次运行新建时间戳文件，保留旧结果。
实验中断时保留已完成组；尚未完成的请求不会被记为成功。

## 8. 自己解释两个问题

1. 上限设置为 128，模型只生成了 74 token 并以 stop 结束，是否正常？
2. 模型回答到半句话就结束，报告是 8 token、length。应优先检查输出预算，还是先换更大的模型？

参考答案：第一种正常，上限不是必须达到的目标；第二种先检查输出预算，不应一开始就归咎于模型大小。
但如果完整回答里事实错误，仅增加预算也不保证修复。
